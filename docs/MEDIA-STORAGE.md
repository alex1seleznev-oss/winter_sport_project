# Фото и видео: хранение и загрузка

## Реальное состояние на 02.10.2026

В существующем Supabase созданы `wsh-originals` (private, 50 MiB на объект) и `wsh-derived` (private, 10 MiB на объект). Разрешены только перечисленные растровые изображения и форматы видео. Оба bucket пусты, публичных Storage-политик нет, пользователей Auth нет. Это подключённая закрытая основа хранения, НЕ работающий публичный видеосервис и НЕ подтверждение возможности загружать сейчас многогигабайтные файлы.

В БД созданы staff_members и media_uploads. Endpoint `/api/media/upload-ticket` по умолчанию возвращает 503 MEDIA_UPLOADS_DISABLED. После включения он требует действующий пользовательский токен, активную серверную роль, правильный формат запроса, закрытый bucket и атомарное резервирование квоты. Привилегированный ключ не отправляется браузеру. Функция reserve_media_upload в БД НЕ установлена: попытка применения была заблокирована инструментом. В коде нет обходного пути без квоты.

## Поток загрузки

Браузер передаёт только описание файла серверу → сервер выдаёт ограниченный подписанный токен → бинарный файл отправляется напрямую в Storage по TUS → приватный объект ожидает проверки → проверяющий воркер создаёт производные файлы → редактор отдельно разрешает публикацию. Не проксировать гигабайты через Next.js/Vercel Route Handler и не хранить видео в PostgreSQL или GitHub.

Supabase рекомендует resumable TUS для файлов больше 6 MB и нестабильной связи, прямой storage-host и блоки 6 MiB. Подписанный токен передаётся через x-signature. TTL подписанного разрешения и срок жизни уже созданного TUS-upload URL — разные ограничения; истечение требует повторной авторизации, а не публикации секрета в URL/логах. Не перезаписывать оригиналы по одному имени.

Официальная документация: https://supabase.com/docs/guides/storage/uploads/resumable-uploads ; https://supabase.com/docs/guides/storage/buckets/creating-buckets .

## Квоты и содержимое

Проектный начальный предел — 50 MiB, а не обещание большого видео. Для многогигабайтных оригиналов сначала выбрать провайдера/регион, проверить фактический тариф и общий лимит проекта, бюджет трафика, резервное копирование и время обработки. Затем отдельно поднять bucket-, серверный и пользовательский лимиты и протестировать файл реального размера. Контракт object storage должен позволять заменить провайдера на S3-совместимое хранилище без переноса публичной логики в обработчики загрузок.

Квота должна резервироваться атомарно, а не запросом «посчитать, затем вставить». Подписанный токен обычно не ограничен заявленным клиентом размером отдельно от максимума bucket: резервировать бюджет консервативно по максимуму объекта и ограничивать число разрешений. Отозванную клиентом попытку нельзя сразу освобождать, пока токен ещё действителен. Спецификация для начала: не более 10 разрешений за скользящие 24 часа на сотрудника, по 50 MiB бюджета на разрешение; функция пока не установлена.

Расширение и MIME клиента не доказывают безопасность. До публикации нужны проверка сигнатуры файла, декодирование в изолированном процессе, антивирусная проверка, ограничения пикселей/длительности/ресурсов, SHA-256, очистка EXIF и проверка лицензии. SVG/HTML/исполняемые файлы не принимаются. Состояние ready задаёт только доверенный воркер. Нельзя выдавать публичный URL на непроверенный оригинал.

## Следующие компоненты — ещё не запущены

Клиент загрузки с прогрессом и восстановлением; безопасная финализация с проверкой фактического объекта; очередь сканирования; оригинал + poster + thumbnail + web-версия; транскодирование HLS для адаптивного просмотра; lifecycle очистка незавершённых попыток и истёкших прав; проверяемое резервное копирование объектов. Политики сроков сначала согласовать, не удалять оригиналы автоматически произвольным заданием.

Месячный бюджет = хранение оригиналов + производные + резервные копии + исходящий трафик + операции + обработка видео. Дешёвый гигабайт хранения не означает дешёвую выдачу видео. Платные тарифы и услуги в этом блоке не подключались.
