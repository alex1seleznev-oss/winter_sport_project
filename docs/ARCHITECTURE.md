# Winter Sports Hub: архитектура платформы

Статус: рабочая основа + явно отделённые будущие компоненты. Дата: 02.10.2026.

## Границы проекта

Репозиторий `alex1seleznev-oss/winter_sport_project`, Supabase `wmiypacyraepljalppub`. Не использовать репозиторий или базу TopRunners. Приложение — модульный Next.js-монолит; выделять отдельные сервисы только для длительного импорта, проверки медиа и перекодирования, а не ради количества микросервисов.

```text
Официальные источники / разрешённые API
              ↓
Получение документа: таймаут, разрешённый хост, размер, версия
              ↓
Парсер конкретного источника → тесты и карантин ошибок
              ↓
Закрытая очередь change_proposals ← сигналы медиа/соцсетей
              ↓
Проверка происхождения и конфликта → решение редактора/верификатора
              ↓
Публичные events / competitions / results / articles / streams
              ↓
Next.js: страницы, календарь, поисковая индексация, виджеты

Оригинал медиа → закрытый bucket → проверка содержимого/прав
              → производные файлы → отдельное разрешение публикации
```

## Данные и их происхождение

Сезон, соревнование/этап и отдельная гонка — разные сущности. Даты тренировочных/организационных дней нельзя автоматически превращать в даты гонок. В текущей базе время хранится в поле `start_time_msk`; переход на `starts_at timestamptz`, IANA-часовой пояс места, точность времени и исходную строку требует отдельной совместимой миграции. До неё интерфейс честно трактует поле как МСК.

Сохранять первичный URL, fetched_at, дату публикации документа при её наличии, parser_version, SHA-256 и external ID. Новый `change_proposals` отделяет `source_authority` от `schedule_certainty`: источник 5/5 может публиковать предварительный проект. Более свежий фан-пост не отменяет официальный документ. Конфликт двух официальных источников не решается одним сравнением дат запроса.

Для каждого изменяемого поля хранить прежнее и предложенное значения, доказательство и решение. Не считать отсутствие строки на странице отменой соревнования. Протоколы учитывать с типом start_list/provisional_result/final_result и версией; это следующий этап нормализации, не уже внедрённая функция. Существующие URL и отметки проверок не переписывать только из-за повторного HTTP-запроса.

## Права и сервисные учётные записи

Публичный клиент имеет только чтение опубликованного набора через RLS. Черновики, журналы, предложения, задания и штатные роли не открыты посетителям. Публикация, проверка и администрирование не должны выполняться одной безграничной ролью.

`staff_members`: owner — назначение ролей и релизы; editor — подготовка/редактура; media_manager — разрешённые медиаоперации; analyst — анализ; auditor — проверка журнала. По умолчанию active=false. Пользователь не может назначить себе роль через user_metadata, форму или JWT-поле собственной записи.

Сейчас таблицы ролей и очередей существуют, но экран входа, управление сотрудниками и выдача прикладных прав ещё не запущены. Service role обходит RLS: это инфраструктурный секрет, а не универсальный токен каждого бота. До запуска рабочих агентов нужны узкие серверные интерфейсы/роли, минимальные гранты, ротация ключей и тесты межролевого доступа. Публичный publishable key не является service secret; безопасность обеспечивается правами, а не сокрытием публичного ключа.

## Семь помощников

source_scout ищет документы; calendar_verifier проверяет календарь; results_verifier проверяет протоколы; broadcast_editor проверяет правообладателя и регион; editorial_assistant пишет только черновики по доказательствам; media_processor проверяет оригиналы и производные; operations_guard следит за ошибками и значимыми изменениями. В реестре все семь имеют enabled=false, execution_status=planned, may_publish=false. Это НЕ семь работающих ботов.

Рабочий цикл: job → lease/блокировка → обработка → proposal → review → публикация → запись результата → уведомление. `idempotency_key` исключает повторное задание. Требуются атомарное получение задания, время аренды, максимум попыток, экспоненциальный backoff и карантин после исчерпания попыток. Таблица jobs создана; воркер и механизм lease ещё не развёрнуты. Редактор не может утверждать собственное изменение чувствительных полей без дополнительной проверки.

Любой текст сайта, PDF, сообщения или файла считается недоверенными данными. Встроенные в него указания не меняют системные инструкции агента, список доменов, получателя уведомлений и права записи. Модель не выполняет произвольный SQL/код, найденный в источнике. В production доступны только типизированные команды.

## Помощники для зрителей и редакции

Будущий зрительский Telegram-бот: календарь, избранные виды спорта и напоминания по подтверждённому времени. Команды /start, /help, /calendar, /settings, /stop; подписки — только по явному запросу, с управлением часовым поясом и удалением данных. Сейчас BotFather-токен и webhook НЕ подключены.

Редакционный бот: показывает diff, ссылку и степень определённости; кнопка одобрения действует только для авторизованного сотрудника, проверяется сервером и связана с версией предложения. Не передавать персональные данные и служебные журналы в общий Telegram-канал. Webhook требует проверки секрета, защиты от повторного update_id и ограничения запросов.

## Наблюдаемость и уведомления

Разделять reachability, parser health, semantic validation, database write и UI freshness. `api/sync` выполняет только первую проверку и прямо это сообщает. Новый timestamp не доказывает полноту импорта. Уведомлять о проверенном изменении даты/времени/места/статуса, новом значимом протоколе, сломанном источнике, сбое публикации или необходимом решении владельца. Не отправлять «изменений нет». Дедупликация по событию/полю/версии, ограничение частоты и эскалация длительного сбоя.

## Развёртывание и восстановление

Изменения кода — отдельная ветка и PR, тесты, сборка и проверка страниц. Не продвигать неработающий preview только потому, что коммит создан. Миграции — совместимые и воспроизводимые; перед разрушительными изменениями резервная копия и проверка восстановления. Откат кода не должен отменять безопасные RLS-ограничения и вновь открывать черновики.

Плановые RPO/RTO надо согласовать с бюджетом; сейчас они не гарантированы. Нужны отдельные резервные копии БД и объектов, шифрование, сроки хранения и тест восстановления. Бэкап PostgreSQL сам по себе не является бэкапом бинарных файлов Storage.
